# `.env*` files: the owner edits them, Jarvis never reads them (2026-10-11)

## The owner's request

> "for credential file handling, I need to be able to edit .env* files in the hud but Jarvis should never be able to read
> them. Jarvis also only gets write access to .env* files ending with .example for example .env.example or
> .env.local.example"

## Today (main at 94979fc)

- **v1's credential-file names are a fixed set** (`jarvis/tools/secrets.py`, `PROTECTED_NAMES`): `.env`, `.env.local` and the token bundles.
  - **So `.env.production`, `.env.staging`, `.env.development.local` and the rest are readable today.** `read_file`, `grep_files`, the shells and the scrub all let them through.
  - `.env.example` is readable on purpose.
- **Writing:** nothing stops a v1 write tool or a shell command from overwriting a `.env*` file.
- **The HUD's file routes** refuse a protected file outright (`hud_api.py` ~637/836/1179). The owner can't open `.env` in the editor either.
- **`terminal_read`** (PR #33) already treats every `.env*` as credential for its rule 1, and so does its printer rule 3.

## The rule (one definition, used everywhere)

- **A credential env file** is any file named `.env` or `.env.<anything>`, at any depth, **except** a name ending in `.example`.
- **What counts as credential:**
  - `.env`, `.env.local`, `.env.production`, `.env.development.local` and `.env.prod.bak` are all credential.
  - `.env.example` and `.env.local.example` are not.
- **Matching:**
  - It is case-insensitive, because Windows drives are.
  - Symlinks are resolved: a symlink named `.env.example` that points at `.env` is credential, and a symlink named `.env` is credential whatever it points at.
- **It lives in one function**, `secrets.is_env_credential(path)`. Every caller asks it; nothing keeps a copy (the CLAUDE.md lesson: two copies drift and the looser one decides).

## What each side gets

| | Read | Write |
|---|---|---|
| **The owner, in the HUD editor** | Yes | Yes |
| **Jarvis: every agent and tool** (v1 tools, the fast path, sub-agents, workflows, tasks, goals, jarvis-mcp, Claude and Codex chats and workers) | **Never** a credential env file. `*.example` freely | **Only** `*.example`. A credential env file is refused |

### The owner's editor (owner-only, HUD listener only)

- Opening and saving a credential env file goes through `projects.owner_only` routes: the HUD listener, with the HUD's Origin (or a same-origin GET, after the `is_owner` fix in the terminal auto-open PR). The API listener never serves its content.
- **The content travels only between disk and the owner's editor.**
  - It is never in the bus, a log line, `log.jsonl`, Discord or `localStorage`.
  - It is never in "Add to chat", Send to chat, an annotation, a diff sent anywhere, or any tool result.
  - The editor marks such a buffer: a lock badge saying "Jarvis can't read this file", and the add-to-chat actions disabled.
- Saving uses the existing mtime check (no clobbering), writes atomically, and keeps the file's mode, with 0600 for a new file.

### Jarvis, reading

1. **v1 tools.**
   - `read_file` and `grep_files` refuse the file, and grep filters it out on both backends.
   - The shells refuse a command naming one, including globs that could match one.
   - `dispatch()`'s scrub withholds the values of every credential env file in the working folder and its parents, not only `.env` and `.env.local`.
2. **The v2 fast path** inherits all of the above.
3. **Claude workers and chats.** The `PreToolUse` hook denies `Read`, `Grep`, `Glob` results and `NotebookRead` on a credential env file, and a `Bash` command naming one. That is the same detector as v1's shell refusal, called, not copied.
4. **`terminal_read`** already refuses a window showing one (rule 1) or a command printing one (rule 3).

### Jarvis, writing

1. **v1 tools.** `write_file` and `edit_file` refuse a credential env file and allow `*.example`.
2. **Shell writes** to a credential env file are **DENY**: never run, never asked, whatever the allowlist says, under `--dangerously-skip-permissions` too. That covers a redirect, `cp`/`mv`/`install`/`tee`/`sed -i`, and the rest of what `protected_state` already parses for gate state. Its machinery is reused by adding the name rule; the parser is not copied. An uncertain write (a glob, an unset variable) asks.
3. **Claude.** The hook denies `Write`, `Edit` and `MultiEdit` on a credential env file, and judges `Bash` writes as above.
4. **Codex.** Its approvals and grants (layer 1) refuse a credential env file.

## Limits, stated plainly

None of this is a boundary against a program running as the owner. That is the standing caveat for `.env` since 2026-07-30.

- **Programs Jarvis runs can still read `.env`.** A dev server loading its `.env` is how env files work, and it has to keep working. A script an agent writes and runs could open the file too.
  - What stops the *contents* reaching the model: v1's scrub, and `terminal_read`'s refusals.
  - For Claude and Codex, Jarvis sees only the tool call, never the tool's output, so there is no scrub on their side.
- **Codex runs its commands inside its own sandbox,** and under AUTO Jarvis is not asked about them. The sandbox lets Codex read the whole disk and write its workspace. So Jarvis's rule reaches Codex only where Codex asks: approvals, extra permissions and grants. Whether Codex's sandbox can be told to deny specific files is a measurement (N-1, below).
- **The real boundary** would be filesystem permissions:
  - agents running as a different Unix user from the one owning the `.env` files;
  - or the files moved somewhere only the owner's editor reaches.
  - That is a larger change, recorded here as the next step if the layers above are not enough.

## Owner's answer (2026-10-11)

- **Q-1, answered:** only names ending in `.example` are open to Jarvis. That covers `.env.example`, `.env.local.example` and any other `.example` variant. The owner said: "keep it to just .env.example or any other .example variants for now". `.env.sample` and `.env.template` stay credential, so Jarvis can neither read nor write them.
